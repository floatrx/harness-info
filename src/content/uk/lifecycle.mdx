## Дошка

У harness-demo кожен етап — колонка на канбан-дошці, а `status` задачі — колонка, в якій вона лежить. Один статус,
одна колонка, один власник. Поки юніт працює над карткою, на ній видно позначку «в роботі».

| Колонка = `status` | Власник             | Що там відбувається                                                                                                | Куди далі                                                     |
| ------------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| `draft`            | ти                  | Пишеш назву і кілька рядків. **Submit** або перетягування рухає далі.                                              | `spec`                                                        |
| `spec`             | writer              | Spec-юніт пише специфікацію.                                                                                       | `plan` · `needs-input`                                        |
| `needs-input`      | ти                  | Відповідаєш на відкриті питання на картці.                                                                         | назад на етап, що питав                                       |
| `plan`             | explorer, planner   | Explorer мапить код; planner пише фази, `scope`, `gate` і критерії.                                                | `planned` · `needs-input`                                     |
| `planned`          | ти                  | Затверджуєш план або повертаєш його planner із коментарем.                                                         | `prototype` для ui-задач, інакше `ready`; `plan` з коментарем |
| `prototype`        | designer, потім ти  | Designer будує прототип; ти приймаєш або коментуєш.                                                                | `ready` · ще одне коло                                        |
| `ready`            | затверджено, чекає  | Поки нічого не працює.                                                                                             | `implementing`, коли стартує implement-юніт                   |
| `implementing`     | tester, implementer | Tester пише тести, implementer — код; harness комітить після зеленого гейту.                                       | `qa` · `parked`                                               |
| `qa`               | qa                  | Проходить критерії на запущеному застосунку.                                                                       | `judge` · `implementing` · `parked`                           |
| `judge`            | judge               | Перезапускає кожну перевірку закриття і пробує відхилити.                                                          | `done` · `implementing`                                       |
| `done`             | runner              | З увімкненим `deliver.pr` runner пушить гілку і відкриває PR, без агента і без токенів. Без нього `done` — кінець. | `delivered` з `deliver.pr`, інакше нікуди                     |
| `delivered`        | —                   | Гілку запушено, PR відкрито.                                                                                       | кінець: мерджить людина                                       |
| `parked`           | ти                  | Зупинено з причиною. **Reopen** повертає назад.                                                                    | статус, з якого запаркували                                   |

Обери статус, щоб побачити його власника і всі виходи з нього. Перемикачі додають переходи, які існують лише з
повною автономією або об'єднаним рев'ю.

## Хто рухає картку

Є лише два види переходів, і вони ніколи не змішуються.

**Ти рухаєш картку**, коли потрібне рішення людини: надіслати чернетку, відповісти на питання, затвердити план
або повернути його, прийняти чи прокоментувати прототип, перевідкрити запарковану задачу. У дашборді це перетягування або кнопки.
Перетягнути можна лише вздовж людського переходу, і дашборд відмовить, поки над задачею працює юніт.

Кожен людський перехід є і командою — для роботи з термінала:

```bash
harness new --title "Dark mode toggle" --draft "Users want a dark theme." --kind ui
harness submit T-007        # draft → spec
harness answer T-007 Q1 a   # answer an open question, with an optional note
harness approve T-007       # planned → prototype (ui) or ready
harness revise T-007 "split criterion 2 into two checks"   # planned → plan, with what the plan should change
harness comment T-007 "move the toggle left of the avatar"
harness accept T-007        # prototype → ready
harness reopen T-007        # parked → the status it was parked from
```

Додай `--project <path>`, якщо ти не в теці проєкту.

**Harness рухає картку** після того, як юніт завершився і його контракти пройшли. Жоден агент не пише `status`
напряму; це робить runner за результатом юніта.

## Інтерв'ю

Агенти питають, а не вгадують. Writer ставить продуктові питання на етапі чернетки; planner — питання, які виникають
лише після читання коду. Обидва користуються одним протоколом:

1. Агент дописує питання в `## Questions` з двома–чотирма варіантами під літерами, рекомендований — першим.
2. Ставить `status: needs-input` і `resume:` зі своїм етапом і завершує юніт зеленим.
3. Дашборд показує відкриті питання як пікер на картці.
4. Твоя відповідь записується під питанням, а питання стає `answered`.
5. Коли відкритих питань немає, harness повертає задачу на етап із `resume`.

```markdown
### Q1 · Where should the toggle live? · open

- (a) Header, right of the nav — recommended: visible on every page
- (b) Settings page only
- (c) Both

> **Answer:**
```

## Етап прототипу

Задачі з `kind: ui` отримують ще один етап перед кодом. Designer будує прототип як маршрут у застосунку і зберігає
його скриншот, `prototype.png` (1440 px завширшки), у теку артефактів задачі. Лише коли застосунок не запускається, він
малює вайрфрейм, `prototype.svg`. Дашборд показує картинку на картці й у шухляді; якщо раунд не лишив картинки, у
`## Log` з'являється нотатка, і маршрут усе одно можна переглянути. Картка зупиняється в `prototype` і чекає на тебе:

- **Accept** переводить задачу в `ready`.
- **Comment** повертає її designer на ще одне коло, з твоїм коментарем у `### Review`.

Кількість кіл обмежує `limits.prototypeRounds`, 3 за замовчуванням. Маршрут прототипу прибирається при доставці,
якщо план не каже його лишити.

## Скільки автономії

За замовчуванням, з `autonomy.mode: gated`, harness зупиняється для тебе двічі на задачу: щоб затвердити план і щоб
переглянути прототип.

На гейті плану його можна й повернути. **Request changes** на вкладці Plan у шухляді або `harness revise` записує
твій коментар у блок `### Review` наприкінці `## Plan`, і задача повертається в `plan`. Наступний раунд плану читає
найновіший коментар і мусить лишити блок без змін. Поки план у planner або поки над задачею працює юніт, повторний запит
відхиляється.

`autonomy.mode: full` вимикає обидва гейти. Спланована задача рухається далі сама, а готовий прототип іде одразу в
`ready`. Дві речі й у повному режимі потребують людини: чернетці потрібен **Submit**, а відкритому питанню — відповідь.

## Гілки і доставка

- Коли задача вперше потрапляє в `implementing`, harness створює гілку `harness/T-NNN-<slug>` від базової гілки
  проєкту. Це єдина гілка, яку дозволяє контракт scope.
- Після кожного implement-юніта із зеленим гейтом harness комітить у цю гілку.
- За замовчуванням доставка — це коміт: з `deliver: { pr: false }` задача закінчується в `done`.
- Перед батчем базова гілка має бути чистою. Supervisor відмовляється працювати на брудному дереві, яке забруднив не він.

### Доставка через pull request

Встанови `deliver.pr: true` у `config.json`, а також `deliver.remote`, якщо remote — не `origin`. Тоді задача в `done`
отримує ще один крок. Його робить сам runner: без агента і без токенів
([`harness/deliver.ts`](https://github.com/floatrx/harness-demo/blob/main/harness/deliver.ts)).

1. Перевіряє контракт гілки: гілка задачі існує, вона попереду базової гілки, і тема кожного коміту починається з
   `T-NNN:`.
2. Пише тіло pull request у `.harness/artifacts/T-NNN/pr-body.md`: ціль зі специфікації, план, кожен критерій
   приймання з ✓ і його командою для `[closes]`, вердикти qa і judge з номерами юнітів і коміти.
3. Пушить гілку через `git push -u <remote> <branch>`.
4. Відкриває pull request через `gh pr create`. Спершу питає `gh pr view <branch>`, тож повтор ніколи не відкриє
   другий.
5. Записує `pr: <url>` у файл задачі і переводить задачу з `done` у `delivered`.

Ніщо ніколи не мерджиться. Harness запускає лише три команди `gh`: `gh auth status`, `gh pr view` і `gh pr create`;
мердж — за тобою. Якщо падає контракт гілки, пуш чи `gh`, задачу паркують із причиною (`parked: deliver: …`), а
**Reopen** повторює крок.

З увімкненим `deliver.pr` supervisor перевіряє все до старту: remote, встановлений і залогінений `gh`, базову гілку на
remote. Якщо чогось бракує, він виходить з кодом 2 і друкує, як це виправити. `HARNESS_GH` підміняє команду `gh` так
само, як `AGENT_CMD` підміняє агента; ним користуються self-тести.

## Скільки коштує одна задача

Повна задача проходить до шести юнітів агентів: spec, plan, prototype, implement, qa і judge, кожен зі свіжим
координатором. Доставка додає крок runner, який не витрачає токенів. Це більше, ніж з'їла б одна довга сесія. Натомість маєш видимість — кожна картка лежить у
колонці свого власника — і чистий контекст для кожної ролі. harness-demo вимірює реальну ціну кожного етапу в
пілоті, перш ніж хтось почне її тюнити.
